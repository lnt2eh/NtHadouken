# Interrupt Descriptor Table (IDT)

The **Interrupt Descriptor Table (IDT)** is a fundamental data structure in the operating system, responsible for dispatching interrupts. Its format is specified by the **CPU** manufacturer, and the operating system must populate it during initialization. The CPU uses the IDT to route interrupts originating from hardware devices or generated by software.

## What Are Interrupts?

Interrupts are signals sent to the processor by hardware devices or software to indicate that an event requires immediate attention. They can be caused by errors (exceptions), hardware devices (such as keyboards or hard drives), or software instructions (such as the `INT` instruction in assembly).

The IDT is essential for managing these interrupts by mapping each interrupt type to a specific handler routine.

## IDTR Register

Each CPU has an internal register called **IDTR**, which stores the virtual address of the IDT. During system initialization, Windows configures the IDTR for each CPU in a multiprocessor system. Each CPU has its own copy of the IDT, pointed to by its own IDTR.

Here is an example of how to inspect the IDTR in WinDbg:

```nasm
0: kd> r idtr
idtr=fffff80377268000
0: kd> ~1
1: kd> r idtr
idtr=ffffc481f7274000
```

## Interrupt Descriptor Table

The IDT contains **256 entries**, each corresponding to an interrupt vector. These entries are used for:

- **Exceptions**: Errors or abnormal events, such as division by zero.
- **Software Interrupts**: Generated by instructions such as `INT`.
- **Hardware Interrupts**: Originating from devices such as keyboards, mice, and others.

On 64-bit systems, each IDT entry is represented by the **KIDTENTRY64** structure. Here is an example of how to inspect an entry in WinDbg:

```nasm
0: kd> dt nt!_KIDTENTRY64 fffff80377268000
   +0x000 OffsetLow        : 0xa200
   +0x002 Selector         : 0x10
   +0x004 IstIndex         : 0y000
   +0x004 Reserved0        : 0y00000 (0)
   +0x004 Type             : 0y01110 (0xe)
   +0x004 Dpl              : 0y00
   +0x004 Present          : 0y1
   +0x006 OffsetMiddle     : 0x7440
   +0x008 OffsetHigh       : 0xfffff803
   +0x00c Reserved1        : 0
   +0x000 Alignment        : 0x74408e00`0010a200
```

### KIDTENTRY64 Structure Fields

- **OffsetLow**, **OffsetMiddle**, **OffsetHigh**: Parts of the offset to the interrupt service routine (ISR).
- **Selector**: Code-segment selector in the GDT (Global Descriptor Table).
- **Type**: Gate type (0xE for Interrupt Gate, 0xF for Trap Gate, and 0x5 for Task Gate).
- **Dpl**: Privilege level required to access the gate.
- **Present**: Indicates whether the entry is present and valid.

The ISR address is obtained by combining `OffsetHigh`, `OffsetMiddle`, and `OffsetLow`. In the example above, the address would be **0xfffff8037440a200**.

## IDT Gate Types

The IDT supports three gate types:

1. **Interrupt Gate (0xE)**:
   - Used for hardware interrupts and some software interrupts.
   - Disables other maskable interrupts while the ISR is executing.

2. **Trap Gate (0xF)**:
   - Used for exceptions.
   - Allows other interrupts to occur while the exception is being handled.

3. **Task Gate (0x5)**:
   - Used to switch to a new task.
   - Contains a selector for a Task State Segment (TSS).

Note that Task Gates are not supported in long mode on the AMD64 architecture.

## Analyzing IDT Entries

We can analyze specific IDT entries using WinDbg. For example, for entry 0x40:

```nasm
0: kd> dt @idtr + @@c++(0x40 * sizeof(nt!_KIDTENTRY64)) nt!_KIDTENTRY64
   +0x000 OffsetLow        : 0x1190
   +0x002 Selector         : 0x10
   +0x004 IstIndex         : 0y000
   +0x004 Reserved0        : 0y00000 (0)
   +0x004 Type             : 0y01110 (0xe)
   +0x004 Dpl              : 0y00
   +0x004 Present          : 0y1
   +0x006 OffsetMiddle     : 0x7440
   +0x008 OffsetHigh       : 0xfffff803
   +0x00c Reserved1        : 0
   +0x000 Alignment        : 0x74408e00`00101190
```

The ISR address for this entry is **0xfffff80374401190**. We can disassemble this address to inspect the instructions:

```nasm
0: kd> u 0xfffff80374401190
nt!KiIsrThunk+0x200:
fffff803`74401190 6a40            push    40h
fffff803`74401192 55              push    rbp
fffff803`74401193 e909060000      jmp     nt!KiIsrLinkage (fffff803`744017a1)
fffff803`74401198 6a41            push    41h
fffff803`7440119a 55              push    rbp
fffff803`7440119b e901060000      jmp     nt!KiIsrLinkage (fffff803`744017a1)
fffff803`744011a0 6a42            push    42h
fffff803`744011a2 55              push    rbp
```

## Interrupt Handling Flow

1. When an interrupt occurs, the CPU uses the interrupt vector to index the IDT.
2. The ISR address is retrieved from the corresponding IDT entry.
3. Control is transferred to `nt!KiIsrThunk`, which pushes the interrupt vector onto the stack and redirects execution to `nt!KiIsrLinkage`.
4. `KiIsrLinkage` locates the **KINTERRUPT** structure associated with the interrupt, using the `InterruptObject` array in **KPCR.CurrentPrcb**.
5. The registered ISR is called through the **KINTERRUPT** structure's `DispatchAddress` field.

## KINTERRUPT Structure

The **KINTERRUPT** structure contains information essential to interrupt dispatch, including:

- **ServiceRoutine**: The interrupt service routine (ISR) registered by the driver.
- **DispatchAddress**: The address to which control is transferred.

Here is an example of how to retrieve the address of a **KINTERRUPT** object:

```nasm
0: kd> uf nt!KiGetInterruptObjectAddress
nt!KiGetInterruptObjectAddress:
fffff801`671797a0 65488b142520000000 mov   rdx,qword ptr gs:[20h]
fffff801`671797a9 4881c240310000  add     rdx,3140h
fffff801`671797b0 8bc1            mov     eax,ecx
fffff801`671797b2 488d04c2        lea     rax,[rdx+rax*8]
fffff801`671797b6 c3              ret
```

The offset of `InterruptObject` in **KPRCB** is **0x3140**:

```nasm
0: kd> dt @$pcr nt!_KPCR -a Prcb.InterruptObject[50]
   +0x180 Prcb                     :
      +0x3140 InterruptObject          : [80] 0xffff8b80`5f730c80 Void
```

## Conclusion

The **IDT** is a critical structure in the operating system, enabling efficient interrupt handling. From system initialization to interrupt dispatch, the IDT and its associated structures, such as **KIDTENTRY64** and **KINTERRUPT**, ensure that the system can respond to hardware and software events quickly and reliably.
