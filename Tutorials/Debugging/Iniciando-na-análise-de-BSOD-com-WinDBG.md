## What Are Windows Dump Files and What Types Are Available?

System dump files are generated by Windows when the operating system enters a critical failure state. These files are intended to help a system administrator understand what caused the crash or BSOD and what happened during the failure.

### Types of Windows Dump Files

Windows provides several types of dump files:

1. Kernel memory dump
2. Small memory dump
3. Automatic memory dump
4. Active memory dump

The main difference between these dump files is their size. A **Complete Memory Dump** is the largest and contains most of the system memory information, including some user-mode memory. An **Active Memory Dump** is somewhat smaller but contains similar information for most purposes. A **Kernel Memory Dump** is smaller and normally omits user-mode memory, while a **Small Memory Dump** is only 64 KB in size.

If you select **Automatic Memory Dump**, the dump file will contain the same information as a Kernel Memory Dump, but Windows has more flexibility when configuring the system paging file size.

The advantage of larger files is that, because they contain more information, they are more likely to help you identify the cause of a failure.

The advantage of smaller files is that they take up less space and are written more quickly. Speed is often valuable; if you are running a server, you may want it to restart as soon as possible after a failure, and the restart cannot occur until the dump file has been written.

```text
Note: After a Complete Memory Dump or Kernel Memory Dump has been created,
you can create a small memory dump from the larger dump file. See the .dump command.
```

## Enabling Kernel-Mode Dump Files

When a failure occurs, the Windows memory dump settings determine whether a dump file is created and how large it will be.

To change the dump settings, follow these steps:

1. Open **Control Panel > System and Security > System**. Select **Advanced system settings**. Under **Startup and Recovery**, select **Settings**.

## Forcing a System Crash

After configuring the type of dump file you want to use for your tests, most system failures should cause a dump file to be written and a blue screen (BSOD) to be displayed.

Microsoft specifies:

**However, there are times when a system freezes without actually initiating a kernel failure. Possible symptoms of this freeze include:**

- **The mouse pointer moves, but you cannot do anything.**
- **The entire display is frozen and the mouse pointer does not move, but paging continues.**
- **There is no response to the mouse or keyboard and no disk activity.**

There are several ways to intentionally generate a BSOD. Today, however, we will focus on using the **NotMyFault** utility from Sysinternals to manually generate a dump file.

1. Download it here: [NotMyFault](https://download.sysinternals.com/files/NotMyFault.zip).
2. When you open it, several crash options will be available (Buffer Overflow, High IRQL Fault, Stack Overflow, etc.). Select one and click **"Crash"**. For this tutorial, I used **"High IRQL Fault (Kernel-Mode)"**.

## Analyzing the Crash with WinDbg

Now that we have crashed the system and Windows has restarted, let's analyze the generated dump file. The dump file is normally located in **C:\Windows** and named **MEMORY.DMP**. This is a large dump file (which can be as large as the system RAM). We also have **minidumps**, which can be found in **C:\Windows\Minidump** and provide a more simplified view of what happened.

Let's analyze a .DMP file inside the Minidump folder. Follow these steps:

1. Open WinDbg as an administrator (the folder where minidumps are stored is privileged).
2. Go to **File > Open Crash Dump**. A file browser will appear. Navigate to **C:\Windows\Minidump** and select the .DMP file. There is no fixed filename; it depends on how many errors have occurred on your system. If you recently configured the VM and triggered a crash with NotMyFault, there will probably be only one file in the folder.
3. After selecting and opening the file in WinDbg, wait for it to finish loading. You can check whether the command prompt displays **"Kd>"**. If it displays **"BUSY"**, it is not ready to receive commands yet.
4. Once WinDbg has finished loading the .DUMP file, run **"!analyze -v"** and wait for the analysis output.

After WinDbg completes its analysis, it will return several parameters that help us understand what happened and caused the machine to crash. For example:

```text
*******************************************************************************
*                                                                             *
*                        Bugcheck Analysis                                    *
*                                                                             *
*******************************************************************************

DRIVER_IRQL_NOT_LESS_OR_EQUAL (d1)
An attempt was made to access a pageable (or completely invalid) address at an
interrupt request level (IRQL) that is too high.  This is usually
caused by drivers using improper addresses.
If kernel debugger is available get stack backtrace.
Arguments:
Arg1: ffffa58b051f7010, memory referenced
Arg2: 0000000000000002, IRQL
Arg3: 0000000000000000, value 0 = read operation, 1 = write operation
Arg4: fffff803708212d0, address which referenced memory
```

This information is sufficient for a basic analysis of what happened on the machine and caused the crash.

Important points to check:

1. **BugCheck code:** In this case, it is **(D1) - DRIVER_IRQL_NOT_LESS_OR_EQUAL**.
2. The analysis output also describes what happened leading up to the failure. Pay attention to this information as well.
3. In addition, the `KeBugCheckEx` function (which causes a Windows BSOD) can receive up to four arguments that provide additional information, such as the address and data involved in a memory corruption error, depending on the value of `BugCheckCode`. Analyze and record each argument to understand what happened.
4. Microsoft provides a public list of all BugCheck error codes. You can access it here: [Bug Check Code Reference](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/bug-check-code-reference2). Once on the page, press **CTRL + F** and enter the error code returned by the debugger. After finding it, open the specific bug check page, which explains the four parameters returned by BugCheck. This can help you reconstruct the sequence of events that led to the critical system error.
